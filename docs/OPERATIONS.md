# Эксплуатация

## Локальная проверка

`START.bat` / `start.ps1` предназначены для демонстрации на одном компьютере. Слушают только `127.0.0.1:8017`. SQLite достаточно для такой проверки; нагрузка и несколько серверов требуют PostgreSQL и отдельно проверенного окружения.

`.dev-secret` — случайный постоянный ключ локального Django. `.demo-credentials.txt`, `.env`, база, закрытые документы и резервные копии исключены из Git. Не публикуйте каталог проекта целиком без проверки этих файлов.

## Чистая серверная среда

1. Отдельные ОС / база / учётная запись и каталог с ограниченными ACL. Не копировать демобазу. Установить зависимости из `requirements-lock.txt`.
2. Создать новый PostgreSQL с отдельным пользователем приложения без административных прав; доступ к БД только с сервера приложения.
3. Создать `.env` на основе `.env.example`; `DJANGO_DEBUG=0`, `DEMO_MODE=0`, `MFA_REQUIRED=1`. Указать реальный `DJANGO_SECRET_KEY`, `DJANGO_ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS` и `POSTGRES_*`. Сгенерировать секрет командой `python -c "import secrets; print(secrets.token_urlsafe(64))"` и хранить его вне исходников.
4. Выполнить:

```powershell
.\.venv\Scripts\python.exe manage.py migrate
.\.venv\Scripts\python.exe manage.py createcachetable
.\.venv\Scripts\python.exe manage.py seed_demo --catalog-only
.\.venv\Scripts\python.exe manage.py createsuperuser
.\.venv\Scripts\python.exe manage.py collectstatic --noinput
.\.venv\Scripts\python.exe manage.py check --deploy
.\.venv\Scripts\python.exe manage.py test
```

5. Через Django admin загрузить реальные территории, СЭС и **явные** маршруты; создать профили, подтвердить пользователей, выдать эпидемиологам необходимые службы. Новая учётная запись без подтверждённого Profile не допускается. Не выдавайте всем роль суперпользователя.
6. Утвердить болезни, проектные анкеты, определения случаев, нумерацию и правила отчётов. Использованную анкету копировать в новую версию; старую не переписывать.
7. Настроить HTTPS reverse proxy перед Waitress, публичные hostname и статические файлы. Waitress запускается `python serve.py` и слушает только loopback. Передавать `Host` и `X-Forwarded-Proto` только от доверенного локального прокси; публичный доступ прямо к Waitress закрыть. Публичный `/static/` соответствует **только** `staticfiles/`. **Не публиковать `private-media/`**: документы выдаются защищённым представлением Django.
8. Настроить службу ОС, журнал ошибок без медицинских payload, синхронизацию времени для TOTP, резервные копии, мониторинг и оповещения об ошибках. Проверить снаружи HTTPS, secure cookies, редиректы, отсутствие доступных служебных файлов и документов.

`check --deploy` оценивает настройки, но не подтверждает безопасность всей системы. Прокси, ACL, шифрование диска и резервных копий, сеть, независимый аудит, расследование инцидентов, пределы хранения и соответствие требованиям Таджикистана проверяются отдельно. Секрет TOTP хранится в БД: шифрование тома / БД и контроль технического доступа обязательны перед реальной эксплуатацией; отдельный KMS / field-level encryption пока не реализован.

## MFA

В учебной среде MFA можно подключить из «Настройки». Для подключения нужен текущий пароль и верный код из приложения. В рабочей среде без MFA приложение направляет на подключение. Код одноразовый в рамках шага времени; повторное использование запрещено. Попытки ограничены.

Если ключ утерян, оператор после отдельной проверки личности может выполнить:

```powershell
.\.venv\Scripts\python.exe manage.py reset_mfa USERNAME --operator SUPERUSER_NAME --reason "Identity verified by the approved recovery procedure"
```

Команда записывает причину и отзывает сессии этого пользователя. В рабочей среде пользователь подключает MFA заново. Наличие административного доступа к серверу само по себе не является проверкой личности пациента или сотрудника.

## Резервное копирование SQLite

Для согласованной копии документов остановите запись в приложение на время копирования. Команда SQLite использует backup API, проверяет `PRAGMA integrity_check` и пишет SHA-256 манифест:

```powershell
.\.venv\Scripts\python.exe manage.py backup_local
.\.venv\Scripts\python.exe manage.py verify_backup "backups\ИМЯ_СОЗДАННОГО_КАТАЛОГА"
```

Копия содержит БД и `private-media/`, если есть документы. Секреты и `.env` резервируются отдельно в защищённом хранилище. Копии с медицинской информацией должны быть зашифрованы и храниться отдельно от рабочего компьютера. Автоматическая отправка копий и расписание этим проектом не настроены.

## Проверка восстановления

1. Создайте **отдельный** каталог / тестовую среду с теми же зависимостями. Не перезаписывайте рабочую базу.
2. Проверьте копию `verify_backup`.
3. В тестовый каталог поместите копию `db.sqlite3` и `private-media/`; используйте отдельный секрет и loopback-порт.
4. Проверьте вход, количество записей, карточки, закрытые документы, отчёты и несколько переходов на тестовых данных. После смены Django secret существующие сессии недействительны; это ожидаемо.
5. Зафиксируйте время и результат. Только после отдельного решения оператора выполняется восстановление рабочей среды.

Команда `verify_backup` действительно открывает резервную БД и проверяет её целостность; это полезная проверка, но она не заменяет полное восстановление отдельного сервера и документов.

Для PostgreSQL нужен `pg_dump` / `pg_restore`, согласованный снимок документов и проверка восстановления. `backup_local` для PostgreSQL намеренно прекращает работу с понятным сообщением; не выдаёт SQLite-копию за копию PostgreSQL.

## Что ещё нужно до реальных пациентов

- Реальная инфраструктура и рабочие справочники; согласованные организационные и нормативные процедуры.
- Полные проверенные переводы и индивидуальные анкеты.
- Испытания PostgreSQL, параллельной записи, объёма данных, конфликтов и резервного восстановления.
- Внешний защищённый аудит, сканирование документов, политики ACL / ключей / секретов и проверка безопасности независимым специалистом.
- Реальный обмен с ID-картой / вакцинацией и каналами СЭС, надёжная очередь внешней доставки.
- Расширенный редактор очагов, утверждённые отчётные формы и фиксация сданных версий.
- План поддержки, обновлений зависимостей, мониторинга и реагирования.

Это границы текущей версии, а не уже выполненные сертификация, интеграция или нагрузочное испытание.
